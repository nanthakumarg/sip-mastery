## 15.1 What SDP does: it describes media, it does not carry it

SIP sets up the call. It does not say where the audio goes, or how it is coded. That is the job of the body: a short text in the **Session Description Protocol**, <Term t="SDP" />. The audio itself travels in <Term t="RTP" /> packets, directly between the phones (Module 16).

| Protocol | Job | Example |
|---|---|---|
| **SIP** | Sets up, changes, and ends the call | `INVITE`, `200 OK`, `BYE` |
| **SDP** | Describes the media: address, port, codecs, direction | `c=IN IP4 192.0.2.10`, `m=audio 49170 RTP/AVP 0` |
| **RTP** | Carries the media | 50 packets per second, 160 bytes of audio each |

SDP is a body in a SIP message, with `Content-Type: application/sdp`. One side sends an <Term t="offer" />: "send my audio here, with one of these codecs". The other side sends an <Term t="answer" />: "agreed, and send mine here, with these". Each side says where it wants to **receive**:

<RfcQuote id="rfc3264-5.1-address" />

Here is Alice's offer. Each line is one letter, `=`, and a value:

```
v=0
o=alice 2890844526 2890844526 IN IP4 192.0.2.10
s=-
c=IN IP4 192.0.2.10
t=0 0
m=audio 49170 RTP/AVP 0 8 101
a=rtpmap:0 PCMU/8000
a=rtpmap:8 PCMA/8000
a=rtpmap:101 telephone-event/8000
a=fmtp:101 0-16
a=ptime:20
```

It says: "I am alice on 192.0.2.10. Send my audio to 192.0.2.10, port 49170, as RTP. I can use PCMU, PCMA, or keypad events, and I prefer PCMU."

## 15.2 Each line: v=, o=, s=, c=, t=, m=, a=, b=

An SDP body has a **session level**, then zero or more **media sections**. Each <Term t="media description" /> starts with an `m=` line. A `c=` or `a=` line at the session level applies to every stream that does not have its own.

<RfcQuote id="rfc8866-5-sections" />

| Line | Name | Example | Meaning |
|---|---|---|---|
| `v=` | Version | `v=0` | Always 0 |
| `o=` | Origin | `o=alice 2890844526 2890844527 IN IP4 192.0.2.10` | Who created the SDP: username, session ID, **version**, address |
| `s=` | Session name | `s=-` | Not used by SIP. It must not be empty, so it is `-` |
| `c=` | Connection | `c=IN IP4 192.0.2.10` | The address that receives the media |
| `t=` | Timing | `t=0 0` | No fixed start or end: SIP starts and ends the session |
| `m=` | Media | `m=audio 49170 RTP/AVP 0 8` | One stream: type, port, transport, formats |
| `a=` | Attribute | `a=rtpmap:0 PCMU/8000`, `a=sendonly` | Everything else |
| `b=` | Bandwidth | `b=AS:64` | The bandwidth the receiver wants, in kbit/s |

The order is fixed, and a receiver may reject an SDP with lines out of order or with a type letter it does not know:

<RfcQuote id="rfc8866-5-order" />

<RfcQuote id="rfc8866-5-unknown" />

`c=` can be at the session level, in each media section, or both. One of the two is required:

<RfcQuote id="rfc8866-5.7-c" />

The `o=` line names the session and its version. The username, session ID, and address stay the same for the whole call. The **version** goes up by one each time this side changes its SDP (15.10).

## 15.3 The m= line: media, port, profile, payload types

```
m=audio 49170 RTP/AVP 0 8 101
  │     │     │       └── formats: payload types, most preferred first
  │     │     └── transport and profile
  │     └── port: where this side receives RTP
  └── media type
```

| Field | Values | Notes |
|---|---|---|
| **Media** | `audio`, `video`, `text`, `application`, `image` | `image` is T.38 fax |
| **Port** | 1 to 65535, or **0** | Port 0: the stream is rejected or removed. RTCP goes to port + 1, unless `a=rtcp` or `a=rtcp-mux` says otherwise |
| **Transport** | `RTP/AVP` | Plain RTP |
| | `RTP/SAVP` | SRTP: encrypted RTP (Module 18) |
| | `RTP/SAVPF`, `UDP/TLS/RTP/SAVPF` | SRTP with feedback; DTLS-SRTP (WebRTC, Module 26) |
| **Formats** | `0 8 101` | RTP payload type numbers, in order of preference |

<RfcQuote id="rfc8866-5.14-m" />

The order matters. The answerer should pick the first format in the offer that it can use, and the offerer sends the first format in the answer.

## 15.4 Payload types: static and dynamic; rtpmap and fmtp

Each RTP packet carries a 7-bit <Term t="payload type" /> number: which codec is in this packet. Some numbers have a fixed meaning in the RTP audio/video profile (RFC 3551). Those are **static** payload types:

| Payload type | Codec | Clock rate | Notes |
|---|---|---|---|
| 0 | PCMU | 8000 | G.711 μ-law, 64 kbit/s. North America and Japan |
| 8 | PCMA | 8000 | G.711 A-law, 64 kbit/s. Most other countries |
| 9 | G722 | 8000 | Wideband, 64 kbit/s. Its clock rate is 8000 although it samples at 16 kHz |
| 18 | G729 | 8000 | 8 kbit/s. Often with `a=fmtp:18 annexb=no` |
| 13 | CN | 8000 | Comfort noise |
| 96–127 | **Dynamic** | Any | Their meaning comes only from `a=rtpmap` in the SDP |

<RfcQuote id="rfc3551-4.5.2-g722" />

Newer codecs have no static number. Opus, AMR-WB, EVS, H.264, and telephone-event always use a **dynamic** number, and `a=rtpmap` says what it means in this SDP:

<RfcQuote id="rfc3551-3-dynamic" />

```
a=rtpmap:<payload type> <encoding>/<clock rate>[/<channels>]
a=rtpmap:111 opus/48000/2         Opus. Always 48000/2, whatever the real rate
a=rtpmap:101 telephone-event/8000 DTMF events (15.7)
a=rtpmap:96 H264/90000            Video always uses a 90 kHz clock
```

<RfcQuote id="rfc8866-6.6-rtpmap" />

A dynamic number with no `a=rtpmap` means nothing: the receiver cannot decode it. Static numbers do not need `a=rtpmap`, but most phones send it anyway, and an answer should:

<RfcQuote id="rfc3264-6.1-rtpmap" />

`a=fmtp` carries settings for one format. SDP does not read them; only the codec does:

```
a=fmtp:111 minptime=10;useinbandfec=1                         Opus: 10 ms packets at least, forward error correction
a=fmtp:18 annexb=no                                           G.729 without silence suppression
a=fmtp:96 profile-level-id=42e01f;packetization-mode=1        H.264 profile and level
a=fmtp:101 0-16                                               telephone-event: the events this side can receive
```

<RfcQuote id="rfc8866-6.15-fmtp" />

## 15.5 Direction: sendrecv, sendonly, recvonly, inactive; hold and resume

Each stream has a direction, from the point of view of the side that writes the SDP. Without a direction attribute, it is `sendrecv`.

| Offer | This side… | The answer must be | Typical use |
|---|---|---|---|
| `a=sendrecv` (or none) | Sends and receives | Any of the four | A normal call |
| `a=sendonly` | Sends, wants nothing back | `recvonly` or `inactive` | **Hold**, with music on hold |
| `a=recvonly` | Receives, sends nothing | `sendonly` or `inactive` | Answer to a hold; a listen-only device |
| `a=inactive` | Neither | `inactive` | Hold with no music; both sides on hold |

<RfcQuote id="rfc3264-6.1-direction" />

<Term t="hold" /> is a new offer. Alice's phone sends a re-INVITE (or an UPDATE) with `a=sendonly`, and Bob's phone answers `a=recvonly`. Bob's audio stops; Alice's phone may send music on hold. To resume, Alice offers `a=sendrecv` again.

<RfcQuote id="rfc3264-8.4-hold" />

<Flow id="hold-resume" eyebrow="Call flow · hold and resume" />

Each side holds by itself. If Bob holds too while Alice holds him, the only answer Alice can give to Bob's `sendonly` is `inactive`: no media either way. When Alice resumes, Bob is still holding, so Bob answers `sendonly`. Each side leaves hold with its own offer. Try it:

Old phones put a call on hold with `c=IN IP4 0.0.0.0`. RFC 3264 replaced this with the direction attributes, but a receiver must still understand it:

RTCP still flows on a held stream. A phone that sees no RTP but still gets RTCP knows the other side is alive (Module 17).

## 15.6 Other attributes: ptime, maxptime, rtcp, rtcp-mux, mid, group:BUNDLE

| Attribute | Example | Meaning |
|---|---|---|
| `ptime` | `a=ptime:20` | This side wants to **receive** 20 ms of audio in each packet. 20 ms is the usual value |
| `maxptime` | `a=maxptime:40` | At most 40 ms of audio in one packet |
| `rtcp` | `a=rtcp:53020` | Send RTCP to this port, not to the RTP port + 1. NAT often makes it needed |
| `rtcp-mux` | `a=rtcp-mux` | RTP and RTCP share one port. Used only if **both** sides include it |
| `mid` | `a=mid:audio` | A name for the stream, used by groups such as BUNDLE |
| `group:BUNDLE` | `a=group:BUNDLE audio video` | Several streams share one address and port. WebRTC uses it (Module 26) |

<RfcQuote id="rfc8866-6.4-ptime" />

<RfcQuote id="rfc5761-5.1.1-answer" />

<RfcQuote id="rfc9143-5-bundle" />

Each side may ask for a different `ptime`: each one says how the other side should send to it. So `ptime` is not negotiated; it is a request.

## 15.7 DTMF with telephone-event

When a caller presses 1 for sales, the IVR must get the digit. Low-rate codecs such as G.729 cannot carry keypad tones well enough for a machine to recognise them, so <Term t="DTMF" /> usually travels as separate RTP packets: **telephone-event** (RFC 4733).

<RfcQuote id="rfc4733-1.2-why" />

```
m=audio 49170 RTP/AVP 0 8 101
a=rtpmap:101 telephone-event/8000
a=fmtp:101 0-16
```

- The number is dynamic: 101 is common, but 96, 100, and others are also used.
- The clock rate usually follows the voice codec: `telephone-event/8000` with G.711, `telephone-event/48000` with Opus.
- `a=fmtp:101 0-16` lists the events this side can receive: 0–9, `*` (10), `#` (11), A–D (12–15), and flash (16).

<RfcQuote id="rfc4733-2.5.1.1-events" />

If the answer has no telephone-event, there are two other ways: the tones inside the audio (works only with G.711), or SIP INFO messages. Module 16 compares the three.

## 15.8 Offer/answer rules

RFC 3264 defines how an answer is built from an offer. The rules are strict, because the two sides match streams **by position**:

| Rule | Why |
|---|---|
| The answer has **exactly the same number** of m= lines, in the same order, with the same media types | Streams are matched by position, not by name |
| To reject a stream, set its **port to 0**. Never remove the m= line | Removing it moves every stream after it |
| An accepted stream has **at least one codec from the offer** | Otherwise the offerer cannot send anything the answerer understands |
| No codec in common: reject the stream with port 0 | No codec in common for any stream: reject the call with 488 |
| Keep the payload type numbers of the offer (SHOULD) | Each side still sends with the number the **other** side wrote |
| Keep the order of the offer (RECOMMENDED) | Then both sides send the same codec |
| The answer has its own `o=` line, `c=`, and ports | It describes where the **answerer** receives |

<RfcQuote id="rfc3264-6-mlines" />

## 15.9 Where the offer goes: early offer or late offer

SIP puts the offer and the answer in fixed places. With only RFC 3261, there are two patterns:

| Pattern | Offer in | Answer in | Who uses it |
|---|---|---|---|
| **Early offer** | INVITE | 200 OK (and the same SDP in 18x, if any) | Most phones and trunks |
| **Late offer** (delayed offer) | 200 OK | ACK | Some PBXs, gateways, and B2BUAs; 3pcc (Module 22) |
| Early offer, reliable 1xx | INVITE | Reliable 183 (100rel) | Early media; mobile networks (15.11) |
| Late offer, reliable 1xx | Reliable 183 | PRACK | Rare |
| In a dialog | re-INVITE or UPDATE | Its 2xx | Hold, codec changes, new streams |

<RfcQuote id="rfc3261-13.2.1-patterns" />

<Flow id="sdp-early-offer" eyebrow="Call flow · early offer" />

With a <Term t="late offer" />, the caller sends no SDP, and the callee must offer in the 200 OK. The caller cannot refuse the offer at that point: it must answer in the ACK, then hang up if it does not like the result.

<Flow id="sdp-late-offer" eyebrow="Call flow · late offer" />

<RfcQuote id="rfc3261-13.2.2.4-ack-answer" />

Only one offer can be waiting at a time in a dialog. If both sides send a re-INVITE with an offer at the same time, that is **glare**: both get 491 Request Pending and try again after a random time (Module 9).

## 15.10 New offers: increment the o= version

Any new SDP from a side — a hold, a resume, a new codec list, a new address — keeps the same username, session ID, and address in `o=`, and increases the version by **exactly one**:

If the version does not change, the receiver may assume the SDP has not changed, and skip it:

## 15.11 SDP in 183, with PRACK or UPDATE

A 183 Session Progress often carries SDP, so that the caller hears a ringback tone or an announcement from the far network: <Term t="early media" />. A normal 1xx is not reliable: it can be lost, and it is never retransmitted. With 100rel (RFC 3262), the 183 is sent reliably, the caller acknowledges it with **PRACK**, and the SDP in it is the real answer:

<RfcQuote id="rfc3262-5-answer-1xx" />

After the answer in a reliable 1xx, either side can send a new offer before the call is answered, with **UPDATE** (RFC 3311). A re-INVITE cannot be sent until the first INVITE has its final response.

The 200 OK to the INVITE then has no SDP, or repeats the same answer. The caller uses the first answer it received:

<RfcQuote id="rfc3261-13.2.1-first-answer" />

Many networks still send SDP in an **unreliable** 183, without 100rel, and repeat the same SDP in the 200 OK. It usually works, but if the 183 is lost, the caller has no early media, and if the 200 OK has different SDP, phones disagree about which one counts.

## Common mistakes

<Mistakes>
  <Mistake title="A private IP address in c=">
    Alice's phone is behind a home NAT router. It writes its own address in the SDP: `c=IN IP4 192.168.1.20`. The NAT router changes the IP header of the packet, but not the text of the SDP. Bob's phone sends its audio to 192.168.1.20, which does not exist on the Internet. Alice's audio reaches Bob, but Bob's never reaches Alice: **one-way audio**. The SIP signaling works perfectly, so the call looks fine in every log.

    <BrokenFixedFlow broken="sdp-private-address" fixed="sdp-public-address" />

    <RfcQuote id="rfc6314-3-private" />

    <p class="fix"><b>Remember:</b> the address in <code>c=</code> and the port in <code>m=</code> must be reachable from the other side. A phone learns its public address with STUN; an SBC can replace the SDP address with its own and relay the media; ICE tries several addresses (Module 20). The address in <code>o=</code> does not matter. Fixing the Contact but not the SDP gives a call that connects with no audio.</p>
  </Mistake>

  <Mistake title="The o= version is not incremented in a new offer">
    Alice's phone puts Bob on hold. Its re-INVITE has `a=sendonly`, but the `o=` version is the same as in the first offer. Bob's phone sees an unchanged version, treats the offer as the SDP it already has, and answers `sendrecv` as before. Alice thinks the call is on hold; Bob's phone keeps sending audio.

    <BrokenFixedFlow broken="hold-same-version" fixed="hold-version-incremented" />

    <p class="fix"><b>Remember:</b> every SDP that differs from the last one this side sent needs the next version, plus one. Repeat the same version only with exactly the same SDP. Turn on <b>Forget to increment o= version</b> in the hold player above and press Hold.</p>
  </Mistake>

  <Mistake title="The answer has a different number or order of m= lines">
    Alice's video phone offers audio and video. Bob's phone has no camera, so it answers with only the audio m= line. Alice matches streams by position: she cannot tell whether the one m= line answers her audio or her video. Most phones reject such an answer and end the call. The same happens when an answer puts video first and audio second.

    <BrokenFixedFlow broken="answer-mline-removed" fixed="answer-port-zero" />

    <RfcQuote id="rfc3261-13.2.2.4-bye" />

    <p class="fix"><b>Remember:</b> one m= line in the answer for each m= line in the offer, in the same order. Reject a stream with <code>m=video 0 RTP/AVP 96</code>: port 0 and one format. A new offer never removes an m= line either; it sets the port to 0, and may reuse that slot later.</p>
  </Mistake>

  <Mistake title="Assuming a dynamic payload type is the same on both sides">
    Alice offers Opus as 111. Bob's phone answers with its own number for Opus, 96. Both are correct. But a gateway that assumes "Opus is 111" sends Opus to Bob as 111, a number Bob's phone did not define, and Bob hears nothing. Or a capture filter that looks for payload type 111 misses half the call.

    ```
    Offer (Alice):   m=audio 49170 RTP/AVP 111 101      a=rtpmap:111 opus/48000/2
    Answer (Bob):    m=audio 3456 RTP/AVP 96 100        a=rtpmap:96 opus/48000/2
    Alice → Bob:     RTP payload type 96     the number from the answer
    Bob → Alice:     RTP payload type 111    the number from the offer
    ```

    <RfcQuote id="rfc3264-5.1-pt-send" />

    <p class="fix"><b>Remember:</b> a dynamic number means something only in the SDP that defines it. Each side sends with the number the <b>other</b> side wrote. Read the <code>a=rtpmap</code> lines of the received SDP; never hard-code 101 for DTMF or 111 for Opus. Try <b>Different payload numbers</b> in the negotiator above.</p>
  </Mistake>

  <Mistake title="No telephone-event, so DTMF fails">
    The caller presses 1 for sales, and nothing happens. The offer had `telephone-event`, but the answer did not: the far side cannot receive RTP events, so the digits are dropped. Or the offer had none, the codec is G.729, and the tones inside the audio are too damaged for the IVR to recognise.

    ```
    m=audio 49170 RTP/AVP 18 101          G.729 and telephone-event: digits as RTP events
    a=rtpmap:18 G729/8000
    a=rtpmap:101 telephone-event/8000
    a=fmtp:101 0-16

    m=audio 49170 RTP/AVP 18              no telephone-event: digits only inside G.729 audio
    ```

    <p class="fix"><b>Remember:</b> offer and accept <code>telephone-event</code> on every audio stream, usually with the clock rate of the voice codec. If a far side does not support it, agree on one other method — G.711 with in-band tones, or SIP INFO — and configure it on both sides (Module 16). Try <b>No DTMF</b> in the negotiator above.</p>
  </Mistake>
</Mistakes>

## Summary

- **SDP** describes the media: the address and port where each side **receives**, the codecs, and the direction. RTP carries the media.
- An SDP body is a **session level**, then one **media section** per `m=` line. The lines have a fixed order. `c=` is at the session level or in every stream.
- `m=audio 49170 RTP/AVP 0 8 101` lists **payload types** in order of preference. 0–95 are **static**; 96–127 are **dynamic** and mean something only with their `a=rtpmap`. `a=fmtp` adds codec settings.
- **Directions**: `sendrecv`, `sendonly`, `recvonly`, `inactive`. **Hold** is a new offer with `sendonly` (or `inactive`); each side holds and resumes by itself.
- **DTMF** travels as **telephone-event** RTP packets, if both sides list it.
- The **answer** has the same m= lines in the same order; it rejects a stream with **port 0** and keeps at least one codec from the offer. Each side sends with the payload numbers the other side wrote.
- **Early offer**: INVITE and 200 OK. **Late offer**: 200 OK and ACK. A **reliable 183** can carry the answer, acknowledged with **PRACK**; **UPDATE** changes the session before the call is answered.
- Every changed SDP has the next **o= version**. Same version means same SDP.
