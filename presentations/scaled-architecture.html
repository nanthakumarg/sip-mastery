    Question 1Who decides, and who only executes?

    The backend owns policy, credit and records. The core node runs SIP, dialogs and media control. The LB tier makes only routing choices: which core node gets a request, and nothing about the call itself.

    DecisionDecided byExecuted by

    Question 3How does a subscriber stay on one core node, and how do calls find a NAT'd client?

    1. Hash on the From URI. Each LB node selects the core node with ds_select_dst("1","1"). A subscriber's REGISTERs and INVITEs land on the same core node, through either LB node.
    2. Path with the received address. The LB node adds Path: <sip:LB;lr;received=sip:client>. The received address is the client's NAT address.
    3. REGISTER goes to the core node over UDP. nathelper sends keepalives only over UDP, so the Path must name UDP. Larger requests on that Path switch to TCP (udp_mtu 1300).
    4. One shared location table. The core node saves the contact and its Path in MySQL. Any core node can find any subscriber.
    5. Calls follow the Path back. The callee's core node sends the INVITE to the LB node in the Path. That LB node sends it to the received address (use_received).
    6. Keepalives from the owner only. Every 30 s the owning core node sends OPTIONS through the Path. Other core nodes skip the contact (filter_server_id).
    7. The hash moves when a core node fails. The LB node skips an inactive core node. The subscriber's next REGISTER re-homes it on another core node.

    Question 4What happens when a component fails?

    The platform fails closed. Without a backend decision, no registration or call starts. No call outlives its allowance.
